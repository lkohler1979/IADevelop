# ambion_execute — Execução do desenvolvimento da atividade AMBION

Quinta etapa da cadeia `ambion_constituir` → `ambion_plain` → `ambion_spec` → `ambion_task` → `ambion_execute` → `ambion_review`. Esta skill escreve código de verdade — ao contrário das quatro anteriores, seu resultado não é só documentação.

Se `docs/agents/constituicao.md` existir, as premissas inegociáveis (seção 8) valem como bloqueante real durante a execução, não como sugestão — se uma tarefa exigir violar uma delas, pare e pergunte ao usuário em vez de prosseguir. Para tarefas isoladas e sem dependência entre si, considere delegar a implementação ao agente `ambion-desenvolvedor` (em paralelo). Antes de aplicar uma migration, acione `ambion-analista-bd`; diante de uma regra de negócio ambígua, acione `ambion-analista-negocio`; para desenhar/validar cobertura de teste de um caso difícil, acione `ambion-analista-teste`.

## Passos

1. Leia `docs/<feature>/STAGE.md` primeiro. Ele diz, por épico, a última tarefa concluída e a próxima etapa (`TASK00N`). Se não existir, pare e diga ao usuário para rodar `ambion_task` primeiro.
2. Confirme com o usuário a ordem de execução dos épicos, caso não seja óbvio pelo `STAGE.md` (por padrão, siga a ordem em que aparecem na tabela "Épicos"; épicos sem dependência entre si podem ser executados em qualquer ordem, épicos com dependência declarada no contrato de dados devem respeitar essa ordem).
3. Para cada épico, execute as `TASK00N.md` pendentes em ordem (a numeração já reflete a ordem de dependência técnica dentro do épico, tipicamente `api` antes de `app` quando um depende do outro — confira a seção "PRDs relacionados neste épico" do `PRD00N.md` correspondente se a ordem não for óbvia). Cada `TASK00N.md` fica direto em `docs/<feature>/<epico>/`, e seus caminhos de arquivo já vêm prefixados por camada (`api/...`, `app/...`, `scripts/...`).
   - **Não releia PRDs ou TASKs anteriores** — a tarefa atual + `STAGE.md` bastam, exatamente como a tarefa promete.
   - Resolva o bloco `0`/`1` (bloqueantes) primeiro; se algum bloqueante não puder ser resolvido sozinho, pare e pergunte ao usuário antes de codar essa tarefa.
   - Implemente os itens do bloco "Implementação desta fatia" na ordem listada, marcando cada checkbox (`- [x]`) no próprio `TASK00N.md` conforme conclui.
   - Rode a validação do bloco "Validação desta fatia" (testes, build, lint — o que o `CONTEXT.md` do domínio tocado indicar como forma de checar) e marque os checkboxes correspondentes só depois de confirmar que passaram.
   - Siga o bloco final "Atualize o STAGE.md antes de encerrar" da própria tarefa — é obrigatório, não pule.
4. Não crie commits nem faça push automaticamente — segue a regra geral do projeto: só commitar quando o usuário pedir explicitamente. Ao final de cada tarefa/épico, resuma o que foi alterado para o usuário poder revisar antes de decidir commitar.
5. Se uma tarefa expuser um bloqueante genuíno (decisão de produto, ambíguidade não coberta pelo PRD, dependência externa) que não estava no bloco `0`, pare, registre em "Bloqueios pendentes" no `STAGE.md` e pergunte ao usuário — não invente a resposta.
6. Quando todos os épicos do `STAGE.md` estiverem marcados como `concluído` (ou o usuário disser que já é suficiente por ora), acione a skill `ambion_review` (via `Skill`) para conferir o resultado contra os PRDs — esse acionamento é seguro (só leitura) e não precisa de confirmação extra.

## Critério de conclusão

Todas as tarefas selecionadas para execução têm seus checkboxes marcados, `docs/<feature>/STAGE.md` reflete o estado real (épicos concluídos, arquivos alterados, decisões tomadas), nenhum bloqueio genuíno ficou sem registrar, e a skill `ambion_review` foi acionada em seguida.
